# FinancialCopilot 记忆系统设计

## 1. 文档状态

- 文档性质：目标架构设计，不代表所有能力已经实现。
- 适用范围：FinancialCopilot 的会话记忆、用户档案、长期事实与程序性经验。
- 当前阶段：现有服务已具备 Redis 短期上下文、Graphiti Episode、长期检索和基础用户画像能力；本文同时描述后续需要补齐的能力。

## 2. 背景与问题

纯向量 RAG 不适合作为记忆系统的唯一实现：

1. 精确标识查询不稳定。手机号、订单号、证券代码等应精确命中，向量召回容易产生噪声。
2. 事实具有时效性。例如用户先说“我住在广州”，之后说“我搬到了上海”，系统既要回答当前状态，也要支持历史回溯。
3. 不同记忆的生命周期不同。当前会话上下文、长期偏好、任务决策和审计记录不能使用同一种存储与淘汰策略。
4. 记忆写入包含风险。模型推断、助手生成内容和用户明确陈述的可信度不同，敏感信息也不能默认长期保存。
5. 删除并非单一操作。会话清空、事实失效、普通检索屏蔽与隐私物理删除具有不同语义。

因此，本系统采用“持久化事件账本 + 多种派生视图 + 策略控制”的架构，而不是将所有内容直接写入向量数据库。

## 3. 设计目标

### 3.1 功能目标

- 保存当前会话所需的短期上下文。
- 将较长对话压缩成可追溯的近期摘要。
- 对手机号、订单号、代码等结构化字段提供精确查询。
- 保存用户明确表达且允许长期保存的偏好、事实和关键决策。
- 支持当前状态查询和指定时间点的历史回溯。
- 支持事实冲突、修正、失效、遗忘和隐私删除。
- 为 Agent 提供与当前任务相关、来源明确、长度受控的上下文。
- 将高质量交互轨迹沉淀为经过审核的候选流程。

### 3.2 非目标

- 不保存每一条模型推断作为长期事实。
- 不把向量相似度当作事实正确性的证明。
- 不允许未审核的交互轨迹直接成为可执行 Skill。
- 不在首期实现跨用户共享记忆或自动共享用户画像。

## 4. 核心原则

1. **Ledger 是事实来源**：Redis、用户档案、图谱和向量索引均是可重建的派生视图。
2. **先隔离，再检索**：所有读写操作必须先限定租户、用户、会话和可见范围。
3. **结构化优先**：能够精确匹配的字段不依赖向量召回。
4. **时间是一等属性**：同时记录现实有效时间和系统记录时间。
5. **来源可追溯**：每条派生记忆能追溯到原始事件或消息。
6. **写入需决策**：由 Policy 判断是否保存、保存到何种作用域以及保留多久。
7. **失效不等于删除**：事实修正通常追加失效事件；隐私删除按合规要求执行物理清理。
8. **降级可见**：依赖异常时返回明确状态，不静默伪造完整结果。

## 5. 总体架构

```text
客户端 / Agent
      │
      ▼
Memory API
      │
      ├── Policy Engine：准入、作用域、敏感度、保留期、冲突策略
      │
      ▼
Event Ledger：只追加的持久化原始事件
      │
      └── Outbox / 异步投影
              ├── Redis 短期窗口
              ├── 会话摘要 View
              ├── 当前用户档案 View
              ├── 时序事实图 View
              ├── 精确键索引
              └── 关键词 / 向量检索索引
```

写请求在 Ledger 持久化后即可获得稳定的 `event_id`。派生视图通过 Outbox 异步更新，失败时可重试和重建。

## 6. 分层记忆

### 6.1 会话元数据

用于当前会话路由，不作为长期记忆：

- `tenant_id`
- `user_id`
- `session_id`
- 入口渠道
- 当前 Agent / 子目标
- 临时上下文标记
- 创建时间与最后活动时间

会话元数据可存入 Redis，但关键身份关系必须能够从持久化会话记录恢复，不能只存在于进程内存。

### 6.2 滑动窗口

保存最近若干条原始消息，为当前轮对话提供低延迟上下文：

- 使用 Redis List 或等价结构。
- 同时受消息数和 Token 数限制。
- 设置可配置 TTL。
- 淘汰消息前应确认其已进入 Ledger；需要长期保留的内容必须已投影到摘要或其他视图。

### 6.3 近期对话摘要

摘要保留对后续任务有价值的信息：

- 关键意图与目标；
- 已确认事实与实体；
- 已完成动作和关键决策；
- 未解决问题、约束和下一步；
- 摘要覆盖的消息序号与来源消息 ID。

建议的数据结构：

```json
{
  "summary_id": "sum_01",
  "tenant_id": "tenant_01",
  "user_id": "user_01",
  "session_id": "session_01",
  "covers_from_seq": 1,
  "covers_to_seq": 40,
  "summary": "用户希望比较两只基金的长期表现。",
  "entities": [],
  "decisions": [],
  "open_tasks": [],
  "source_message_ids": ["msg_01", "msg_40"],
  "model_version": "model-name",
  "generated_at": "2026-09-27T10:00:00Z"
}
```

构造上下文时使用“最近有效摘要 + 摘要之后的原始消息”，避免摘要和原文重复占用 Token。

### 6.4 用户结构化档案

用户档案属于精确读取的派生视图，不通过自由文本语义搜索重建。金融场景的初始维度包括：

- 风险偏好；
- 专业水平；
- 关注板块；
- 持仓风格；
- 基金偏好；
- 决策风格；
- 语言与输出偏好；
- 用户明确确认的关键约束。

当前值以 `(tenant_id, user_id, dimension)` 为唯一键。每个值必须保留来源、置信度和有效时间。低置信度或影响较大的推断应请求用户确认，不直接替换当前值。

### 6.5 长期事实记忆

长期事实适合存储稳定且可能跨会话复用的内容，例如用户明确陈述的偏好、持有关系、历史决策和业务事件。

每条事实至少包含：

```json
{
  "fact_id": "fact_01",
  "tenant_id": "tenant_01",
  "user_id": "user_01",
  "session_id": "session_01",
  "subject": "user_01",
  "predicate": "risk_preference",
  "object": "稳健",
  "memory_type": "PROFILE",
  "source_type": "USER_STATEMENT",
  "source_event_ids": ["evt_01"],
  "confidence": 0.95,
  "valid_from": "2026-09-27T10:00:00Z",
  "valid_to": null,
  "recorded_at": "2026-09-27T10:00:02Z",
  "superseded_at": null,
  "visibility": "PRIVATE",
  "sensitivity": "FINANCIAL"
}
```

## 7. Agentic Memory 三件套

### 7.1 Ledger：原始事件账本

Ledger 采用只追加语义，保存：

- 用户和助手消息；
- 外部工具调用及结果摘要；
- 系统执行的业务动作；
- 事实提取和确认事件；
- 事实撤回、替代和删除请求；
- Policy 决策结果。

每个事件必须包含：

- 全局唯一 `event_id`；
- 调用方提供的 `idempotency_key`；
- 租户、用户和会话作用域；
- 事件类型及版本；
- 事件发生时间与系统接收时间；
- 来源和关联 ID；
- Payload 及敏感度；
- 写入者或服务身份。

重复的 `idempotency_key` 必须返回第一次写入的结果，避免网络重试产生重复记忆。

### 7.2 Views：派生视图

View 面向具体读场景构建：

- 当前用户状态卡；
- 当前会话上下文；
- 本次任务相关历史摘要；
- 当前有效事实；
- 指定时间点的事实快照；
- 精确键索引；
- 关键词、向量和图关系索引。

View 必须记录投影版本和最后处理的事件位置，以支持追赶、重放与重建。

### 7.3 Policy：记忆控制策略

Policy 在写入和读取阶段执行。

写入决策建议返回：

```json
{
  "decision": "STORE",
  "scope": "USER",
  "memory_type": "PROFILE",
  "sensitivity": "FINANCIAL",
  "retention_days": 365,
  "confidence": 0.92,
  "requires_confirmation": false,
  "reason": "用户明确表达长期风险偏好"
}
```

Policy 至少覆盖：

- 明确陈述、模型推断和助手输出的不同可信等级；
- PII、金融信息等敏感内容的准入和保留期限；
- 用户、租户、会话和任务作用域；
- 低置信度、冲突和高影响信息的确认机制；
- 子目标切换时上下文保留或清理；
- 用户遗忘请求和合规删除；
- 防止 Prompt Injection 直接改变记忆策略。

## 8. 双时间与冲突处理

### 8.1 时间字段

- `valid_from`：事实在现实世界开始有效的时间。
- `valid_to`：事实在现实世界结束有效的时间，空表示当前有效。
- `recorded_at`：系统首次记录该事实的时间。
- `superseded_at`：该记录在系统中被新版本替代的时间。

读取当前状态的条件：

```text
valid_from <= now AND (valid_to IS NULL OR valid_to > now)
AND superseded_at IS NULL
```

历史查询必须先在数据库层应用时间和作用域过滤，再排序、召回和截断；不能先取语义 Top-K 后在应用层过滤。

### 8.2 冲突规则

当新事实与当前事实冲突时：

1. 用户明确修正优先于模型推断。
2. 已确认事实优先于未确认事实。
3. 同等来源下，现实有效时间较新的事实优先。
4. 无法判断时保留多个候选，标记 `AMBIGUOUS`，不得静默覆盖。
5. 更新当前 View 时，旧事实设置 `valid_to`，新事实设置 `valid_from`；Ledger 保留完整事件历史。

例如用户从广州搬到上海：广州记录的 `valid_to` 等于上海记录的 `valid_from`，当前查询返回上海，历史时点查询仍能返回广州。

## 9. 检索设计

检索采用分阶段路由：

1. 强制应用 `tenant_id`、`user_id`、`session_id` 和可见范围过滤。
2. 识别手机号、订单号、证券代码等结构化标识，查询精确键索引。
3. 查询结构化用户档案和当前有效事实。
4. 对剩余自然语言需求执行关键词、向量和图检索。
5. 应用有效时间、来源可信度和敏感度策略。
6. 合并、去重、重排并控制 Token 预算。
7. 返回事实、来源、有效时间、置信度和检索方式。

建议响应结构：

```json
{
  "results": [
    {
      "fact_id": "fact_01",
      "content": "用户风险偏好为稳健",
      "memory_type": "PROFILE",
      "match_type": "EXACT",
      "score": 1.0,
      "confidence": 0.95,
      "valid_from": "2026-09-27T10:00:00Z",
      "valid_to": null,
      "source_event_ids": ["evt_01"]
    }
  ],
  "degraded": false,
  "warnings": []
}
```

## 10. 写入流程

1. API 校验身份、作用域、事件格式和幂等键。
2. Policy 判断是否保存、记忆类型、作用域、敏感度和保留期。
3. 将原始事件和 Policy 决策持久化到 Ledger。
4. 在同一事务中写入 Outbox。
5. 后台 Worker 更新 Redis、摘要、档案、图谱和检索索引。
6. 投影失败时指数退避重试；超过阈值进入死信队列并告警。
7. API 或任务状态接口可返回投影进度。

不允许出现“Redis 写入成功但 Ledger 永久丢失”的状态。Graphiti 或 Embedding 服务不可用时，原始事件仍应可靠保存，派生投影稍后恢复。

## 11. 遗忘与删除语义

系统提供四类不同操作：

| 操作 | 语义 | Ledger | 派生视图 |
|---|---|---|---|
| `session_clear` | 清空短期上下文 | 保留 | 删除 Redis 会话窗口 |
| `retract` | 声明事实错误或不再有效 | 追加撤回事件 | 标记失效 |
| `hide` | 不参与普通检索 | 追加隐藏事件 | 从检索结果屏蔽 |
| `hard_delete` | 隐私或合规物理删除 | 删除敏感 Payload，仅保留无敏感信息凭证 | 清理缓存、图、向量及备份策略覆盖范围 |

删除操作必须返回 `operation_id`、状态和各存储的处理结果。异步删除只有在所有必需存储确认后才标记完成。

## 12. 程序性记忆

高质量交互轨迹可以生成“候选流程”，但不能直接发布为可执行 Skill。生命周期为：

```text
CANDIDATE → EVALUATED → APPROVED → PUBLISHED → DEPRECATED
```

候选流程至少包含：

- 适用场景与前置条件；
- 标准步骤和必要参数；
- 输入输出 Schema；
- 校验规则与安全限制；
- 来源轨迹的脱敏引用；
- 测试案例和评测结果；
- 版本、审批人和回滚策略。

涉及退款、交易或外部副作用的流程必须人工审批，并在执行前再次校验权限和关键参数。

## 13. API 语义建议

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/v1/sessions` | 创建或恢复会话 |
| `POST` | `/v1/sessions/{sid}/messages` | 幂等写入消息事件 |
| `GET` | `/v1/sessions/{sid}/context` | 获取摘要和滑动窗口组成的上下文 |
| `DELETE` | `/v1/sessions/{sid}/context` | 仅清理短期上下文 |
| `POST` | `/v1/memories/search` | 按作用域检索当前有效记忆 |
| `POST` | `/v1/memories/search/temporal` | 查询指定有效时间的记忆 |
| `POST` | `/v1/memories/{id}/retract` | 追加事实撤回事件 |
| `POST` | `/v1/privacy/deletions` | 创建异步隐私删除任务 |
| `GET` | `/v1/privacy/deletions/{id}` | 查询删除进度 |
| `GET` | `/v1/users/{uid}/profile` | 精确读取当前结构化档案 |
| `GET` | `/v1/users/{uid}/profile/history` | 读取档案变化历史 |

服务身份通过认证信息确定租户；请求体中的 `tenant_id` 不能覆盖认证得到的租户。

## 14. 可靠性与可观测性

需要监控：

- Ledger 写入成功率与延迟；
- Outbox 积压量和最大延迟；
- 各 View 投影成功率；
- Redis、Neo4j、Embedding 和 LLM 的可用性；
- 精确检索与语义检索命中率；
- 冲突、歧义和确认请求数量；
- 删除任务完成时间及失败存储；
- 单次上下文的 Token 数和摘要压缩率。

日志不得直接输出完整消息、手机号、账户信息、API Key 或未脱敏的金融数据。

## 15. 验收指标

首期建议达到：

- 同一幂等键重复提交不会生成重复 Ledger 事件。
- 任意用户检索结果中不得出现其他用户的私有记忆。
- 精确标识查询准确率达到 100%。
- 当前状态查询能正确处理连续事实更新。
- 历史时点查询覆盖边界时间、迟到事件和无效区间。
- Redis、Graphiti 或 Embedding 短暂不可用时，Ledger 事件不丢失且投影可恢复。
- 摘要可以追溯到来源消息，并且不会遗漏未完成任务和关键约束。
- `retract`、`hide`、`hard_delete` 的行为和结果可审计。

评测集至少包括：

- 手机号、订单号、证券代码精确查询；
- “广州 → 上海”等事实更新；
- 相同名称、不同实体的歧义；
- 跨用户和跨租户隔离；
- 低置信度画像推断；
- 用户要求遗忘；
- 依赖失败后的补偿和重放。

## 16. 当前实现与目标差距

当前 `memory-service` 已实现：

- Redis 会话消息窗口和 TTL；
- 消息写入 Graphiti Episode；
- Graphiti 长期搜索；
- 基础时点结果过滤；
- 基于 LLM 的用户画像提取接口。

尚需补齐的关键能力：

1. 持久化 Ledger、事件 ID、幂等键和 Outbox。
2. 强制租户、用户和会话过滤。
3. 独立的结构化用户档案 View。
4. 摘要生成、版本管理和来源追溯。
5. 数据库层双时间查询和显式冲突处理。
6. 精确键索引及检索路由。
7. 可执行 Policy Engine。
8. 完整的撤回、隐藏和隐私删除流程。
9. 投影重试、死信和可观测性。
10. 程序性记忆的审核、评测和发布流程。

## 17. 分阶段落地

### 阶段一：安全与一致性基线

- 增加租户、用户、会话作用域；
- 建立 Ledger、幂等写入和 Outbox；
- 明确 API 错误及降级状态；
- 建立结构化用户档案 View；
- 修复遗忘接口语义。

### 阶段二：时间与检索能力

- 实现双时间数据模型；
- 增加精确键索引；
- 将作用域和时间过滤下推到数据库；
- 增加混合检索、来源和置信度返回；
- 建立隔离、冲突和历史回溯评测集。

### 阶段三：摘要与策略

- 增加增量会话摘要；
- 实现 Policy Engine；
- 完善敏感度、保留期和用户确认；
- 增加投影重建、监控和告警。

### 阶段四：程序性记忆

- 生成脱敏候选流程；
- 建立离线评测和人工审批；
- 实现版本化发布、灰度和回滚。

首期应优先保证隔离、可追溯和不丢数据，再逐步提高召回效果与自动化程度。
